# Performance benchmarks

Mining throughput and memory for `repo-intel`, measured with
`benchmarks/bench.py` on synthetic repositories generated by
`benchmarks/genrepo.py` (200 rotating source files, 1–3 files changed per commit,
10 authors, ~⅓ of commits are bug-fixes).

Reproduce:

```bash
python -m benchmarks.bench 1000 5000 20000 --jobs 2
# large repo:
python -m benchmarks.genrepo /tmp/repo_100k 100000 200 10
```

## Environment

- 2 vCPU container, Python 3.11, PyDriller 2.12 / GitPython 3.1.
- Wall time via `time.perf_counter`; **peak** = `tracemalloc` peak Python
  allocation; **RSS** = process max resident set (`ru_maxrss`, includes the git
  subprocess).

## Results

| commits | files | serial s | commits/s | peak MB (py) | parallel s (j=2) | speedup | RSS MB |
|--:|--:|--:|--:|--:|--:|--:|--:|
| 1,000   | 200 | 7.3   | 137 | 2.5  | 5.1   | 1.43× | 35  |
| 5,000   | 200 | 38.2  | 131 | 11.3 | 24.9  | 1.53× | 56  |
| 20,000  | 200 | 158.2 | 126 | 41.3 | 96.5  | 1.64× | 127 |
| 100,000 | 200 | ~794* | ~126 | ~205* | **467.4** | ~1.70×* | 193 |

\* The 100k row was measured for the **parallel** path (100,000 commits in
**467 s = 214 commits/s**, peak 79 MB, RSS 193 MB). Serial figures for 100k are
extrapolated from the stable 126 commits/s and the linear memory trend, not run
to completion.

## Reading the numbers

- **Throughput is stable with size** — ~126–137 commits/s serial from 1k to 20k,
  no super-linear degradation. Cost is dominated by PyDriller's per-commit diff,
  which is O(changes), not O(history).
- **Memory is bounded and linear** — Python peak grows ~2 MB per 1,000 commits
  (the commit list + per-file stats); RSS stays under 200 MB at 100k commits.
  Nothing accumulates per-file diff objects, so there is no blow-up on large
  histories.
- **Parallel mining scales with cores** — 1.43×→1.64× on 2 vCPUs (each worker
  drills an isolated `--local` clone, then histories are merged; the result is
  bit-identical to serial, asserted in `tests/test_hardening.py`). The speedup
  ceiling is the core count minus clone/merge overhead; on an 8-core host expect
  ~4–5×.

## When to use what

- Day-to-day / CI on one repo: **serial** (`repo-intel analyze`).
- First mine of a very large repo: **`--jobs N`** (N ≈ cores).
- Re-analysis after new commits: **`--incremental`** — drills only the delta, so
  it is near-constant time regardless of total history size.
